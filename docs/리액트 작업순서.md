# 리액트 작업순서

목적: 이 문서는 React(프론트엔드)에서 현재 FastAPI 서버(SignSense Inference Server)의 REST 엔드포인트 및 WebSocket(시그널링) 엔드포인트를 연결하여
실시간 추론 → 저장 → 피드백 흐름을 구현하는 정확한 순서를 제공합니다.

대상 엔드포인트
- GET  /                : 서버 상태 확인
- GET  /health          : 모델 로드 상태 확인
- GET  /model/status    : 모델 로드 상태 및 경로 정보
- GET  /config          : 서버 구성(프레임 수, 타임아웃 등)
- GET  /client          : 테스트용 HTML(참고)
- POST /simulate/predict: 스모크 테스트용 더미 추론
- WS   /ws/{session_id} : WebSocket 시그널링 엔드포인트 (JWT는 쿠키에서 읽음)
- GET  /api/diagnostics/status : 진단 라우터 상태 확인
- POST /api/diagnostics/echo   : 진단 라우터 에코 엔드포인트 (스모크용)

문서 구성 및 체크리스트
1. 전제조건(환경/인증) 확인
2. REST 엔드포인트 연결 순서 및 예제 코드
3. WebSocket(시그널링) 연결 순서 및 예제 코드
4. WebRTC(DataChannel)를 통한 프레임 전송 전략
5. 메시지 타입별 처리 흐름(`meta`, `save_learning`, `flush`)
6. 에러/디버깅 체크리스트
7. 권장 보완 및 서버-클라이언트 조정 포인트

---

1) 전제조건 (작업 전에 확인할 점)
- React 앱에서 서버에 접근 가능한지 확인 (CORS 설정 필요할 수 있음).
  - 개발: create-react-app 개발 서버(`http://localhost:3000`)에서 FastAPI(`http://localhost:8000`) 접근 시 서버에 CORS 허용 필요.
- 인증 토큰 처리 방식 확인
  - 현재 서버는 WebSocket에서 JWT를 `websocket.cookies.get(settings.COOKIE_ACCESS_TOKEN_NAME)`로 읽습니다.
  - 따라서 React에서 로그인 후 토큰을 쿠키(특정 이름)로 세팅해야 WebSocket에서 인증이 동작합니다.
  - 권장: 서버가 이미 로그인 엔드포인트로 쿠키를 발급한다면 별도 조치 불필요. 아니라면 토큰 저장 방식(쿠키/세션)을 서버와 맞춥니다.
- HTTPS 환경: 쿠키(Secure) 또는 SameSite 정책 때문에 HTTPS 환경에서 동작이 더 안정적입니다.

2) REST 엔드포인트 연결 (순서 및 예시)
- 공통: `fetch` 또는 `axios`를 사용합니다. (예제는 fetch 기반)

2.1 서버 상태 확인 (루트)
- 용도: 서버가 실행 중인지 빠르게 확인
- 요청: GET /

예시:
```js
// src/api/status.js
export async function getServerStatus(baseUrl = "http://localhost:8000"){
  const res = await fetch(`${baseUrl}/`);
  return res.json();
}
```

2.2 헬스 체크(모델 로드 여부)
- 용도: 모델 로드 여부로 UI 표시(예: "모델 로딩 중")
- 요청: GET /health

예시:
```js
export async function getHealth(baseUrl = "http://localhost:8000"){
  const res = await fetch(`${baseUrl}/health`);
  return res.json();
}
```

2.3 모델 상태 / 설정 조회
- GET /model/status, GET /config — 앱 초기화 시 한 번 불러와 디바이스/모델 경로/수집 파라미터 사용

2.4 스모크 테스트 (옵션)
- POST /simulate/predict — 스모크용으로 로컬에서 추론 흐름 확인

예시:
```js
export async function simulatePredict(baseUrl = "http://localhost:8000"){
  const res = await fetch(`${baseUrl}/simulate/predict`, { method: 'POST' });
  return res.json();
}
```

3) WebSocket 시그널링 연결 (핵심 흐름)
- 목적: 서버와 시그널링 메시지(메타데이터, flush, save_learning 등)를 주고받음. 실제 프레임(이미지/바이트)은 WebRTC DataChannel로 전송하는 것이 설계상 의도입니다.
- 엔드포인트: ws://host:port/ws/{session_id}

사전 조건
- 쿠키에 인증 토큰이 있어야 서버가 연결을 허용합니다. (서버 코드에서 cookie 이름은 settings.COOKIE_ACCESS_TOKEN_NAME)
- 만약 쿠키로 전달하기 어렵다면 서버를 소폭 수정하여 쿼리 파라미터 또는 Sec-WebSocket-Protocol/Authorization 헤더로 토큰을 받게 변경해야 합니다.

3.1 기본 WebSocket 연결 예시 (브라우저)
```js
// src/ws/signaling.js
export function createSignalingSocket(sessionId, baseUrl = 'ws://localhost:8000'){
  const url = `${baseUrl}/ws/${sessionId}`;
  const ws = new WebSocket(url);

  ws.onopen = () => {
    console.log('WS open');
  };

  ws.onmessage = (ev) => {
    const data = JSON.parse(ev.data);
    // data.type에 따라 처리 (meta_ack, inference_result, learning_ack 등)
    console.log('WS msg', data);
  };

  ws.onclose = () => { console.log('WS closed'); };
  ws.onerror = (e) => { console.error('WS error', e); };

  return ws;
}
```

3.2 메시지 송신 규칙
- meta: 단어(퀴즈) 메타를 먼저 전송
  - { type: 'meta', word_pk: 123, word_name: '안녕' }
  - 서버는 collector.meta에 저장하고 meta_ack 반환
- save_learning: 클라이언트가 학습데이터 저장 요청 시
  - { type: 'save_learning' }
  - 서버는 저장을 백그라운드로 실행하고 learning_ack 반환
- flush: 수집이 끝나면 flush를 보내 추론을 실행하고, 서버는 추론 결과와 함께 schedule_quiz_save를 스케줄
  - { type: 'flush' }
  - 서버는 { type: 'inference_result', result: ... } 를 반환

4) WebRTC + DataChannel을 통한 프레임 전송 전략 (권장)
- 설계 의도: WebSocket은 시그널링(텍스트 메시지) 전용이며, 실시간 프레임은 WebRTC DataChannel 또는 MediaStream을 통해 전달하는 것이 권장됩니다.
- 순서 (간단 시나리오):
  1. React에서 RTCPeerConnection 생성
  2. DataChannel 생성(예: 'frames') 또는 getUserMedia로 비디오 캡처
  3. 시그널링 WebSocket으로 offer/answer/ICE 후보 교환
  4. DataChannel이 open되면, 각 프레임(이미지 바이너리 또는 JPEG 바이트)을 전송
  5. 서버 쪽에서 DataChannel을 통해 수신된 프레임을 collector.frames에 저장하도록 처리(서버의 aiortc 구현 필요)

- React 예시(요약):
```js
const pc = new RTCPeerConnection();
const dc = pc.createDataChannel('frames');

dc.onopen = () => { /* send binary frames: dc.send(blob) */ };

dc.onmessage = (e) => { /* optional: server에서 에코 메시지 */ };

// 이후 offer 생성 -> ws.send({type:'offer', sdp:...}) 등 시그널링을 통해 교환
```

참고: 현재 서버의 WebSocket 핸들러는 텍스트 메시지 수신 루틴과 collector.frames 를 사용하는 구조를 가지지만,
실제 DataChannel을 통해 바이트를 collector.frames에 연결하려면 서버측 aiortc DataChannel 수신 코드가 필요합니다. 서버 코드에서 DataChannel 수신이 이미 구현되어 있다면 React는 위 방식으로 구현하면 됩니다.

5) 메시지 타입별 상세 처리 (React에서 구현해야 할 로직)
- 초기화(페이지 진입)
  1. GET /config 호출하여 TARGET_FRAME_COUNT 등 파라미터 읽기
  2. UI에 파라미터 반영(프레임 개수, 타임아웃)
- 세션 시작
  1. 세션 ID 생성(랜덤 또는 서버 발급) → sessionId
  2. WebSocket 연결: ws://.../ws/{sessionId}
  3. WebRTC 피어 연결(선택): offer/answer 교환을 통해 DataChannel 연결
- 단어(퀴즈) 시작
  1. UI에서 단어 선택 → ws.send(JSON.stringify({type:'meta', word_pk, word_name}))
  2. 서버로부터 meta_ack를 받으면 녹화 시작
- 프레임 전송(수집)
  1. DataChannel이나 MediaStream 캡처를 통해 프레임을 전송
  2. 동일한 세션의 collector.frames에 서버에서 누적
- flush(추론 실행)
  1. 클라이언트가 수집을 마치면 ws.send(JSON.stringify({type:'flush'}))
  2. 서버가 inference_result를 반환하면 UI에 결과 표시
  3. 서버는 schedule_quiz_save를 백그라운드로 스케줄하여 npy/CSV 저장 수행
- 학습 데이터 저장
  1. 사용자가 저장을 요청하면 ws.send(JSON.stringify({type:'save_learning'}))
  2. 서버가 learning_ack를 반환하면 사용자에게 저장 요청 수락을 알림

9) 저장(Quiz & Learning) 트리거 — React에서 반드시 알아야 할 정확한 동작

핵심 요약:
- `save_quiz` (퀴즈 저장)는 별도의 REST 엔드포인트로 노출되어 있지 않습니다. 서버는 WebSocket 흐름에서 `flush` 메시지가 들어오면 `run_inference`를 실행하고 그 결과를 기반으로 내부적으로 `schedule_quiz_save(...)`를 호출하여 저장을 트리거합니다.
- `save_learning` (학습 데이터 저장)은 클라이언트가 WebSocket으로 `{type: 'save_learning'}` 메시지를 보낼 때 서버에서 `schedule_learning_save(...)`를 호출하여 저장을 트리거합니다.

동작 매핑(액션 -> 메시지/엔드포인트 -> 서버 동작 -> 응답):
- 사용자가 수집 완료 후 퀴즈 저장을 원함
  - React: ws.send(JSON.stringify({ type: 'flush' }))
  - 서버: collector.frames를 사용해 run_inference(predictor, frames) 실행 → inference_result 수신 → schedule_quiz_save(frames, inference_result, session_id, meta) 스케줄
  - 서버 응답(동기): ws로 { type: 'inference_result', result: <inference_result> } 전송
  - 서버 동작(비동기): 백그라운드에서 landmark 추출 후 `storage.save_quiz(...)` 호출하여 npy/csv 저장
- 사용자가 수집된 프레임을 학습 데이터로 저장하고자 할 때
  - React: ws.send(JSON.stringify({ type: 'save_learning' }))
  - 서버: collector.frames와 collector.meta를 사용하여 schedule_learning_save(frames, session_id, meta) 호출(비동기)
  - 서버 응답(동기): ws로 { type: 'learning_ack', status: 'accepted' } 반환
  - 서버 동작(비동기): landmark 추출 후 `storage.save_learning(...)` 호출하여 npy/csv 저장

팁: 서버는 저장을 비동기(백그라운드 task)로 처리하므로 클라이언트는 저장 완료 여부를 직접 수신하지 못합니다. 필요 시 서버측 schedule_quiz_save/schedule_learning_save 내부에서 저장 완료 후 WebSocket으로 알림을 보내도록 서버를 확장할 수 있습니다.

React 예제: WebSocket으로 저장 트리거 보내기
```js
// sendFlush.js
export function sendFlush(ws){
  // 수집이 끝난 뒤 호출
  ws.send(JSON.stringify({ type: 'flush' }));
}

export function sendSaveLearning(ws){
  ws.send(JSON.stringify({ type: 'save_learning' }));
}
```

서버가 REST 엔드포인트로 직접 저장을 노출하도록 변경할 경우(선택 사항)
- 장점: WebSocket을 사용하지 않는 환경에서 저장을 트리거할 수 있음(테스트/외부 연동용)
- 단점: 프레임 데이터 전송 방식(base64 또는 multipart)를 정의해야 하며 대용량 업로드에 성능 이슈가 있을 수 있음

REST 예시(서버에 구현된 경우 사용 가능한 호출 형식)
POST /api/internal/save-quiz
Request JSON body example:
{
  "session_id": "sess1",
  "frames": ["<base64-jpeg-1>", "<base64-jpeg-2>", ...],
  "meta": {"user_id": "u1", "word_pk": 10, "word_name": "안녕"},
  "inference_result": {"predicted": "안녕", "score": 0.92}
}

응답 예시: {"ok": true, "status": "scheduled"}

권장: 리얼타임 수집/추론/저장은 WebSocket + WebRTC(DataChannel) 기반으로 유지하고, REST 저장 엔드포인트는 디버그/백업용으로 선택적으로 추가하세요.
